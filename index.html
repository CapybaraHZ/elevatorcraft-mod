01 · 项目概述

11 项需求，全部落地

ElevatorCraft 在 Minecraft 中实现了一套可管理、可鉴权、可监控的电梯系统。下表是需求与实现的对应关系。

#需求实现方式

2.1为什么最终选择 1.21.8 而不是 26.1？

26.1 虽然已有 Fabric API（0.146.x+26.1.x）与 Loom 支持，但它是一次底层 API 大重构，与 1.21.x 的差异远超普通版本升级。实测在 26.1 上编译时，本模组用到的以下 API 全部失效：

1.21.x 写法（本工程使用）26.1 的变化
ResourceLocation改名为 Identifier
CompoundTag 直接读写改为 ValueInput / ValueOutput
Block#onPlace / onRemove移除，改为 affectNeighborsAfterRemoval 等
Block#useWithoutItem移除 / 改名
Block#getShape改为 getShapeForEachState
DirectionProperty移除，统一用 EnumProperty<Direction>
BlockEntityType.Builder移除，改用 FabricBlockEntityTypeBuilder
BlockRenderLayerMap + RenderType改为 ChunkSectionLayer
SavedData.Factory改为 SavedDataType + Codec
Entity#getPersistentData()移除
Item#appendHoverText 旧签名增加 TooltipDisplay 参数

因此，为了让交付物「真正可编译、可运行」，本工程以 1.21.8 为实际目标，并在第 10 节给出迁移到 26.1 的完整对照清单。

03 · 架构设计

四层架构，职责清晰

客户端只渲染快照，服务端权威校验，业务数据集中在世界级管理器，方块只存引用。

客户端 (Client)
ElevatorCraftClient · TerminalScreen · PanelScreen · MonitorScreen · BaseElevatorScreen
—— 只渲染快照，不持有业务状态
↕ OpenScreenPayload / TerminalSyncPayload (S2C) · TerminalActionPayload / PanelRequestPayload (C2S)
网络层 (Network)
ModNetworking —— 服务端权威校验（门锁 / 刷卡 / 楼层 / 距离）
↕
业务层 (Domain)
ElevatorManager (SavedData) ← 世界级单例
  ├─ ElevatorGroup ← 一台电梯的全部状态
  ├─ FloorEntry ← 一层（门 + 面板列表）
  └─ ElevatorSize ← 规格枚举
AccessControl ← 刷卡鉴权规则
↕
方块层 (Block)
ElevatorCarBlock · ElevatorDoorBlock · CallPanelBlock · ControlPanelBlock · TerminalBlock
ElevatorControllerBlockEntity ← 只存「我属于哪台电梯」

3.1三个核心设计决策

🗄️

① 数据集中，方块只存引用

一台电梯有几十个方块。业务数据全部放在 ElevatorManager（世界级 SavedData）里，方块实体只保存一个 UUID groupId 引用。好处：一份数据天然同步、存档只写一份、方块被破坏后数据仍在。

🛡️

② 服务端权威

客户端只发「意图」（我要去 3 楼），所有校验在服务端完成：距离校验、刷卡校验、楼层权限校验。杜绝客户端伪造。

🪟

③ 不用 vanilla Menu/Container

原版 GUI 需要注册 MenuType + 实现槽位同步，对「纯信息面板」是纯负担。本模组改为「服务端发快照 → 客户端 setScreen」，零槽位样板代码。

05 · 关键实现说明

核心逻辑

5.1楼层检测（需求 6）

规则：任意一个电梯门 + 至少一个控制面板 = 一层。

// ElevatorManager.rebuildFloors
for (int y = minY; y <= maxY; y++) {
    for (int dx = -radius; dx <= radius; dx++) {
        for (int dz = -radius; dz <= radius; dz++) {
            cursor.set(origin.getX() + dx, y, origin.getZ() + dz);
            BlockState state = level.getBlockState(cursor);
            if (state.is(ModBlocks.ELEVATOR_DOOR)) {
                doorByY.putIfAbsent(y, cursor.immutable());
            } else if (state.is(ModBlocks.CONTROL_PANEL)) {
                panelsByY.computeIfAbsent(y, k -> new ArrayList<>()).add(cursor.immutable());
            }
        }
    }
}
// 只有门没有面板 → 不构成楼层
for (var e : doorByY.entrySet()) {
    List<BlockPos> panels = panelsByY.getOrDefault(e.getKey(), List.of());
    if (panels.isEmpty()) continue;
    detected.add(new FloorEntry(detected.size(), e.getKey(), e.getValue(), panels, existingName));
}

要点：扫描范围轿厢 y ± (96 下 / 320 上)，水平半径 = 规格边长 + 6；同一 y 的多个门/面板合并为一层；按 y 升序重新编号；保留已有自定义楼层名。

5.2电梯移动（需求 1）

采用「轿厢 y 逐格移动 + 实体搬运」而非「逐方块移动」：

// ElevatorManager.tick —— 每 tick 调用一次
int currentY = group.carY();          // = carOrigin.getY()
int targetY  = targetFloor.y();
int step = Integer.signum(targetY - currentY);
if (step == 0) { arrive(...); return; }

int newY = currentY + step;
carryEntities(level, group, currentY, newY);   // 搬运轿厢内实体
group.setCarOrigin(group.carOrigin().atY(newY));

if (newY == targetY) arrive(level, group, target);
// 实体搬运：把轿厢 AABB 内的实体一起抬升/下降
AABB box = new AABB(o.getX(), fromY, o.getZ(),
                    o.getX() + fp, fromY + ElevatorSize.INNER_HEIGHT, o.getZ() + fp);
for (Entity e : level.getEntities((Entity) null, box, Entity::isAlive)) {
    e.teleportTo(e.getX(), e.getY() + dy, e.getZ());
    e.setDeltaMovement(0, 0, 0);
    e.hurtMarked = true;   // 强制客户端同步位置
}

为什么不用逐方块移动：逐方块移动需要每 tick 破坏+放置几十个方块 → 触发大量方块更新、光照重算；跨区块时可能触发区块加载造成卡顿；玩家站在轿厢里会被方块挤压。速度：每 tick 1 格 ≈ 0.05 秒/格，10 层楼约 1.5 秒。

5.3刷卡鉴权（需求 4）

// 数据模型（存于物品数据组件）
public record ElevatorCardData(
        UUID groupId,          // 绑定到哪台电梯
        AccessMode mode,       // ALL_FLOORS | SELECTED_FLOORS
        Set<Integer> floors,   // 指定楼层（用楼层序号，不用坐标）
        UUID owner             // 持卡人（审计用）
) { ... }
// 鉴权规则（AccessControl）
public static boolean hasValidCard(Player player, ElevatorGroup group) {
    if (!group.cardEnabled()) return true;      // 未启用刷卡 → 放行
    if (player.isCreative()) return true;       // 创造模式 → 放行
    return cardMatches(player.getMainHandItem(), group)
        || cardMatches(player.getOffhandItem(), group);
}

public static boolean canAccessFloor(Player player, ElevatorGroup group, int floorIndex) {
    if (!group.cardEnabled() || player.isCreative()) return true;
    ElevatorCardData data = findCard(player, group);
    if (data == null) return false;
    if (data.mode() == AccessMode.ALL_FLOORS) return true;   // 全部楼层
    return data.floors().contains(floorIndex);               // 指定楼层
}
授权模式行为
ALL_FLOORS可到达该电梯的所有楼层
SELECTED_FLOORS仅可到达卡上登记的楼层集合

5.5门锁系统（需求 8）

两级锁：① 门级锁 ElevatorDoorBlock.LOCKED 方块状态；② 整梯锁 ElevatorGroup.locked，锁住时所有呼梯请求返回 LOCKED。

// 管理终端远程锁梯：同时更新数据与所有门方块
case TOGGLE_LOCK -> {
    boolean newLocked = !group.locked();
    group.setLocked(newLocked);
    for (FloorEntry f : group.floors()) {
        ElevatorDoorBlock.setLocked(level, f.doorPos(), newLocked);
    }
}

5.6监控系统（需求 5）

MonitorScreen 是只读视图，视觉上模拟真实电梯监控屏：左侧楼层灯带（当前层青色高亮、目标层琥珀色、其他灰色）；右侧状态卡（运行中/静止、当前层、目标层、门锁状态）。数据来源是 ElevatorSnapshot，与终端共用同一份快照，因此监控不会额外增加网络开销。

5.7外呼面板三样式（需求 2）

public enum CallStyle implements StringRepresentable { UP, BOTH, DOWN }

// 目标楼层解析逻辑
case UP   -> 找 panelY 上方最近的楼层
case DOWN -> 找 panelY 下方最近的楼层
case BOTH -> 轿厢在下方则上行，否则下行（自动判断）

碰撞箱为 2px 薄片（Block.box(0,0,0,16,16,2) 按朝向旋转），非满方块。

5.8连接器（需求 7）

两步操作：① 手持连接器右键电梯轿厢 → 记录 groupId；② 手持连接器右键控制面板 → 触发 rebuildFloors，该面板即成为该电梯的楼层组件。之后即可在管理终端「楼层」标签页看到并选择该楼层。

07 · 材质资源方案

程序化生成，风格统一

搜索了 Minecraft 电梯模组素材与工业金属贴图，存在两个问题：风格不统一（不同来源的分辨率、色调、光照方向不一致）、授权不明（多数素材未标注可商用/可再分发许可）。因此采用程序化生成（tools/gen_textures.py）。

📐

统一规格

全部 16×16，符合原版像素密度。

🎨

统一调色板

冷灰金属 + 青色指示灯，全模组一致。

⚖️

无版权风险

可自由修改，改调色板常量即可全量同步。

11 · 崩溃修复记录（v1.0.1）

启动崩溃已定位并修复

v1.0.0 在 Minecraft 1.21.8 上启动即崩溃。已读取崩溃报告、定位根因、修复代码并重新编译，且实际启动客户端验证通过。

💥 崩溃现象

游戏在加载模组阶段直接崩溃，崩溃报告关键堆栈：

java.lang.ExceptionInInitializerError
Caused by: java.lang.NullPointerException: Block id not set
    at net.minecraft.world.level.block.state.BlockBehaviour.<init>(BlockBehaviour.java)
    at net.minecraft.world.level.block.Block.<init>(Block.java)
    at com.elevatorcraft.block.ElevatorCarBlock.<init>(ElevatorCarBlock.java)
    at com.elevatorcraft.registry.ModBlocks.<clinit>(ModBlocks.java)

11.1根因

Minecraft 1.21.2 起，方块与物品的 Properties 在构造对象前必须已经设置注册 ID。

  • 旧代码把「构造方块」直接写在 ModBlocks 的 static final 字段初始化里，且 BlockBehaviour.Properties.of() 之后没有调用 setId(...)。
  • 1.21.2+ 的 Block 构造函数会校验 properties.id，为空即抛 NullPointerException: Block id not set。
  • 由于发生在 <clinit>（类静态初始化）阶段，异常被包装成 ExceptionInInitializerError，模组加载失败 → 游戏崩溃。
  • 物品同理：Item.Properties 也需要 setId(...)，否则报 Item id not set。
💡 性质

这是 1.21.2 引入的「注册表 ID 前置」机制，属于版本 API 变更，不是资源或 Mixin 问题。

11.2修复内容

文件修复
registry/ModBlocks.java新增 props(name, …) 统一入口，内部调用 Properties.of().setId(ResourceKey.create(Registries.BLOCK, id))；注册动作移入 register()
registry/ModItems.java新增 itemProps(name) 统一入口，内部调用 new Item.Properties().setId(ResourceKey.create(Registries.ITEM, id))；注册动作移入 register()
registry/ModComponents.java拆分为「字段构造 + register() 显式注册」
registry/ModItemGroups.java同上
registry/ModBlockEntities.java同上
ElevatorCraft.javaonInitialize() 按依赖顺序显式调用各 register()：组件 → 方块 → 物品 → 物品栏 → 方块实体 → 网络包 → 事件

核心改动：把「构造」与「注册」分离，并保证每个 Properties 都带 ID。

// 修复前（会崩溃）
public static final Block ELEVATOR_CAR_STANDARD = new ElevatorCarBlock(
        BlockBehaviour.Properties.of().mapColor(MapColor.METAL)...);   // ❌ 没有 setId

// 修复后
public static final Block ELEVATOR_CAR_STANDARD = new ElevatorCarBlock(
        props("elevator_car_standard", MapColor.METAL, 4.0F, 10.0F, SoundType.METAL));

private static BlockBehaviour.Properties props(String name, ...) {
    return BlockBehaviour.Properties.of()
            .setId(ResourceKey.create(Registries.BLOCK, id(name)))   // ✅ 关键
            .mapColor(color).strength(hardness, resistance).sound(sound);
}

13 · 名称乱码修复 + 游戏内教程（v1.0.3）

物品名称乱码已定位并修复，同时加入游戏内教程

v1.0.2 贴图已正常，但背包里模组物品的名称显示为原始翻译键（如 item.elevatorcraft.elevator_car_standard）。已定位根因、修复并重新编译，同时新增完整中文 tooltip 与一本游戏内「电梯手册」。

🧱 用户截图确认的现象

物品栏中模组物品的悬停名称显示为 item.elevatorcraft.elevator_car_standard 这类未翻译的原始键名（不是编码乱码、也不是问号方块）—— 这是 Minecraft 在找不到对应翻译键时回退显示键名本身的典型表现。

13.1根因（1.21.8 的翻译键前缀规则）

Minecraft 1.21.8 中，BlockItem 不会自动使用 block. 前缀。Item.Properties 的默认 descriptionId 是 item.<ns>.<path>，只有显式调用 useBlockDescriptionPrefix() 才会切换为 block.<ns>.<path>。

环节说明
原版怎么做原版 net.minecraft.world.item.Items#registerBlock(...) 创建 BlockItem 时显式调用了 useBlockDescriptionPrefix()，所以原版方块的翻译键是 block.minecraft.stone。
本模组漏了什么早期版本的 ModItems 直接用 new BlockItem(block, props)，漏了 useBlockDescriptionPrefix() → 方块的 BlockItem 去找 item.elevatorcraft.xxx。
为什么显示乱码语言文件里只有 block.elevatorcraft.xxx，没有 item.elevatorcraft.xxx → 查找失败 → 界面回退显示原始翻译键，即用户看到的「乱码」。

根因通过反编译 Minecraft 1.21.8 字节码确认：Item.Properties 的 effectiveDescriptionId 默认返回 ITEM_DESCRIPTION_ID，仅当 useBlockDescriptionPrefix() 被调用后才返回 BLOCK_DESCRIPTION_ID。

持久化实体保存 GroupId 与规格；重启后自动恢复，实体丢失时每 1 秒兜底补建

14.3架构：实体与方块的分工

com/elevatorcraft/ ├── entity/ │ └── ElevatorCarEntity.java # 轿厢实体：移动 / 停靠 / 载人 / 持久化 ├── client/ │ ├── ElevatorCarRenderer.java # 用电梯材质渲染立方体轿厢 │ └── ElevatorCarRenderState.java # 渲染状态（规格 / 运行中） ├── elevator/ │ └── ElevatorBuilder.java # 一键召唤 / 自动搭建 / 实体兜底 ├── item/ │ └── ElevatorSummonItem.java # 召唤器物品（三种规格） └── registry/ └── ModEntities.java # 实体类型注册
为什么门 / 面板 / 终端仍是方块？

它们需要「贴墙」「薄碰撞箱」「右键交互」，用方块实现最自然，也与既有系统（刷卡、门锁、监控、终端 GUI）完全兼容。只有「会动的轿厢」变成了实体。
